# Межисточниковые дубли

Дата: 19.11.2026. Статус: утверждён пользователем для реализации; реализован режим смысловых пометок.

## Цель и согласованный подход

Сократить повторные показы одной вакансии из разных источников, сохранив отдельные похожие позиции. Пользователь согласовал рекомендацию: подтверждённые повторы объединять, сомнительные показывать с пояснением; сначала проверить новый алгоритм без скрытия смысловых совпадений.

SQLite остаётся основным архивом. Существующие фильтры вакансий, коды писем и отметки Google Forms сохраняются. Obsidian и экспорт Markdown в эту работу не входят.

## Подходы

1. Только прямые ссылки и ID: просто и надёжно, но не помогает публикациям без исходной ссылки.
2. Ссылки/ID и осторожное сравнение описаний: выбранное направление; требует обогащения карточек и архива, позволяет объяснять сомнения.
3. Нечёткое сравнение заголовков с автоматическим скрытием: отвергнуто, поскольку объединяет разные команды и позиции.

## Решение для первого выпуска изменений

Текущий точный дедуп продолжает работать. Новое подтверждение идентичности — одинаковая каноническая ссылка на конкретную вакансию либо одинаковые работодатель/система найма и ID вакансии. Сам номер без пространства имён не уникален. Общие страницы карьеры, формы без ID, почта рекрутера, Telegram-контакты и ссылки на подборки не подтверждают идентичность. Не удалять значимые параметры URL с ID; удалять только известные параметры отслеживания.

При конфликте двух явных ID или нескольких неоднозначных ссылках автоматического объединения нет. Разные карточки одного сайта не объединяются по одному названию. Противоречия команды, грейда и обязанностей блокируют смысловое объединение; отсутствие сведений не считается совпадением.

Смысловое сравнение в первом этапе только предлагает возможный дубль. Оно не объединяет сущности, не наследует отметки и не скрывает карточки. Отдельного автоматического скрытия по ответу LLM в этом этапе нет. Возможное его включение — отдельное решение после наблюдения.

## Архив и совместимость

Добавить отдельные сущности, не менять ключи и коды существующего ledger:

- Вакансия: внутренний стабильный ID, подтверждённые идентификаторы работодателя/системы найма.
- Публикация: source + external_id + URL конкретной вакансии (пост-подборка может содержать несколько вакансий), исходный текст, описание полной карточки, название, компания, команда, грейд, ссылки отклика, даты публикации/первого наблюдения, связь с вакансией.
- Связь отправки: ledger.dedup_key и внутренний ID вакансии. Нынешние code/status остаются в ledger; при необходимости новая история отправок хранит соответствия старых и новых кодов без изменения контракта форм.
- Предположение о дубле: пара публикаций/вакансий, основания, версия алгоритма и результат; отдельная запись, не подтверждённая связь.

Миграция добавочная и повторяемая. Старые строки без описаний сохраняются; отсутствующие сведения не восстанавливаются догадками. Подтверждённые связи позволяют учитывать applied/reviewed у любой связанной записи без срока; applied приоритетнее reviewed. Предположения об идентичности не переносят статусы.

В первую очередь обогащать детальные карточки jabka: работодатель, описание и исходные ссылки. Для Telegram использовать текст и ссылки поста. Прочие адаптеры передают уже доступное описание и идентификаторы; универсальный обход произвольных ссылок не нужен. Ошибка обогащения не теряет исходную карточку и не становится доказательством дубля; остаётся доступен текущий точный дедуп.

Архивировать обработанные кандидаты на вакансию, включая подавленные подтверждённые дубли, а не любые посты. Новые записи, связи и решения записывать в одной транзакции с seen/bookmarks/ledger после успешной отправки, либо в существующей ветке успешного пустого выпуска. При SMTP failure, rollback и dry-run они не сохраняются. Служебный журнал runs сохраняет нынешнее поведение.

## Поиск совпадений

1. Сравнить подтверждённые идентификаторы внутри запуска и с архивом. Для обычных ранее показанных вакансий окно 30 дней; applied/reviewed без ограничения. Вне окна обычная вакансия может снова попасть в письмо по существующей политике, архивная связь сохраняется.
2. Для оставшихся искать кандидатов за 10 дней по первому наблюдению, сравнивая также текущий выпуск. Нужны известный одинаковый работодатель и содержательные данные о команде/задачах/требованиях; общие слова «аналитик», SQL, Python, удалёнка не достаточны. Окно не продлевается каждым повтором публикации. Старые отмеченные записи без описаний не получают искусственного смыслового совпадения.
3. Использовать сравнение содержательных частей описания, исключив общий шаблон условий работодателя. На первом этапе достаточно детерминированного консервативного сопоставления; пороги и выделение частей — выбор исполнителя с обязательными отрицательными тестами. Отдельная зависимость от embeddings или новый внешний сервис не требуются. Не обещать распознавание любых перефразировок.
4. Для каждого предположения сохранять объяснение и ссылку на предыдущую карточку; выбирать максимум одно наиболее обоснованное для подписи. Совпадения по цепочке A≈B≈C не превращать в идентичность A=C.

## Поведение письма

Подтверждённые совпадения в одном выпуске дают одну карточку и ссылки на все публикации. Представителя выбирать предсказуемо: прямая карточка работодателя, затем наиболее полная публикация; выбор не изменяет фильтры и корзину молча. При противоречиях условий сохранять более осторожную оценку формата.

Подтверждённое повторение уже показанной вакансии в окне не отправляется. Сомнительная карточка остаётся в своей корзине, со своим кодом отметки и строкой «Возможно, уже присылали: [дата — название — источник]». Для совпадения внутри текущего выпуска текст «Возможный дубль: …». Подписи и ссылки присутствуют в HTML и текстовой версии, строки экранируются. Обновить статистику: точные повторы и предполагаемые повторы считать отдельно.

## Проверка и включение

Обязательные примеры:

- jabka «Аналитик данных для команды модерации» и FreeWorkFeed/4295 «Аналитик данных в команду модерации»: одинаковая исходная Avito vacancy 20883 подтверждает дубль, если ссылка извлечена из обеих публикаций; без неё возможна только обоснованная пометка по описанию.
- «Аналитик данных для оценки качества модерации» сохраняется отдельно.
- Одинаковые заголовки разных команд/ID, пустая компания, одинаковые шаблонные условия и общий контакт не дают автоматического объединения.
- Проверить границы 10/30 дней, applied/reviewed старше окна, новые отметки текущего запуска, независимость кодов сомнительных карточек, несколько вакансий в подборке, порядок источников, повторяемость миграции, rollback/SMTP failure/dry-run.

Сначала прогнать полный набор тестов и dry-run на копии SQLite с заблокированной отправкой. Сверить сохранность старых ledger/code/status и integrity_check. В рабочей базе не выполнять исследовательских переписываний; тестовые письма не отправлять.

После внедрения наблюдать минимум шесть успешных штатных выпусков: новые смысловые совпадения только помечаются. В итогах указать число подтверждённых повторов, предположений и обнаруженных ошибочных сопоставлений. Автоматический переход к скрытию смысловых совпадений запрещён: шесть выпусков — срок наблюдения, а не доказательство качества.

## Границы и решения исполнителя

В этой работе нет массовой перезагрузки старых публикаций, замены SQLite, нового внешнего AI-сервиса, пользовательского интерфейса разметки или удаления истории. Исполнитель выбирает имена таблиц/индексов, лимиты сетевого обогащения и пороги консервативной пометки, документирует их и покрывает регрессиями. Если данных не хватает, сохраняет вакансию без необоснованного решения о дубле.
